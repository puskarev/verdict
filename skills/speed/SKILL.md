# Speed audit: что из советов по скорости реально нужно этому проекту

Цель — не применить всё подряд, а **честно отсеять**. Большинство пунктов чек-листа к конкретному проекту не относится, и это нормальный результат. Вред от ненужной оптимизации (лишние зависимости, сложность, кэш, который надо инвалидировать) считается так же серьёзно, как польза.

Если передан аргумент (`$ARGUMENTS`) — проверяй только эти пункты или эту область. Иначе — весь список.

## Шаг 1. Пойми проект

Прежде чем смотреть пункты, определи и коротко запиши:
- **Тип**: веб-фронтенд / бэкенд API / fullstack / iOS / Android / бот (Telegram и т.п.) / CLI / библиотека / статический сайт.
- **Стек**: язык, фреймворк, база, ORM, хостинг (по `package.json`, `requirements.txt`, `pyproject.toml`, `Podfile`, `Package.swift`, `build.gradle`, `Dockerfile`, конфигам деплоя).
- **Масштаб**: примерный объём кода, есть ли признаки реальной нагрузки (кол-во пользователей неизвестно — так и скажи, не выдумывай).
- **Что уже есть**: кэш, очереди, CDN, мониторинг, пулы, индексы.

Пункты, которые заведомо не относятся к типу проекта (например, Core Web Vitals для Telegram-бота или CDN для iOS-приложения), сразу помечай «не применимо» одной строкой, без раскопок.

## Шаг 2. Пройди чек-лист

Для каждого применимого пункта **найди доказательство в коде** (`файл:строка`) — есть проблема или нет. Не пиши «возможно стоит» без конкретного места. Если проверить нельзя без запуска/доступа к проду — так и скажи и опиши, как проверить.

## Шаг 3. Вердикт по каждому пункту

Для каждого пункта — один из вердиктов:
- 🔴 **Нужно** — проблема найдена в коде и заметно влияет на пользователя/нагрузку.
- 🟡 **Можно позже** — улучшение реальное, но эффект небольшой при текущем масштабе, или стоит сделать при росте.
- ⚪ **Не нужно** — проблемы нет, уже сделано, или цена (сложность, зависимости, поддержка) выше пользы для этого проекта. Обязательно скажи *почему* не нужно.
- ➖ **Не применимо** — не относится к типу проекта.

## Шаг 4. Отчёт

Формат ответа:

1. **Проект в двух строках**: тип, стек, что уже оптимизировано.
2. **Главное** — топ-3…5 пунктов «Нужно», отсортированных по соотношению польза/усилия. Для каждого: что не так (`файл:строка`), что предлагаешь сделать, сколько усилий (S/M/L), какой ожидаемый эффект, риски.
3. **Таблица по всем пунктам**: `№ | Пункт | Вердикт | Почему (одной фразой, со ссылкой на код)`. Пункты «не применимо» можно свернуть в одну строку списком номеров.
4. **Чего точно не стоит делать** — пункты, которые выглядят соблазнительно, но этому проекту навредят или бесполезны (например, Redis в маленьком проекте, OpenTelemetry в монолите на одного разработчика, мемоизация «везде»).
5. **Как проверить**, если что-то нельзя оценить по коду (нужен прод, профайлер, EXPLAIN на реальных данных).

## Правила

- **Ничего не меняй в коде.** Это только анализ. В конце спроси, какие пункты внедрить. После «ок» внедряй по одному пункту и проверяй результат после каждого.
- Не устанавливай пакеты и не трогай инфраструктуру без явного согласия.
- Не завышай важность: если проект маленький и без нагрузки, честно скажи, что большая часть пунктов сейчас не нужна.
- Для больших проектов параллель исследование по областям (фронт / бэк / инфра) через субагентов, но вердикты выноси сам.
