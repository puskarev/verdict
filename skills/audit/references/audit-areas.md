# Области аудита

В каждой области указано, к каким типам проектов она применима, что проверять и **когда находка становится ненужной**. Последнее важнее всего: это защита от карго-культа.

Типы проектов: `web` (сайт или фронтенд), `api` (бэкенд), `mobile` (iOS/Android), `bot`, `lib`, `cli`.

---

## P: Скорость и производительность
**Применимо:** все типы. Подробный чек-лист в соседнем скиле `speed-audit` (`../../speed/SKILL.md` относительно этого файла) (31 пункт + M1–M6 для мобилок + B1–B5 для ботов).

Главное, что проверить в первую очередь:
- N+1 и запросы в цикле; отсутствие индексов под частые WHERE/ORDER BY.
- Списки без пагинации или лимита.
- Последовательные независимые await.
- Блокирующие операции в async-коде или на главном потоке (мобилки).
- Тяжёлые картинки и бандл (web), холодный старт (mobile).
- Повторные одинаковые запросы.

**Не нужно, когда:** данных мало и роста не ожидается; Redis, CDN, OpenTelemetry и горизонтальное масштабирование для проекта без нагрузки; мемоизация без подтверждённой проблемы.

## S: Безопасность
**Применимо:** все, кроме чисто статических сайтов без форм (для них только заголовки и зависимости).

Начни с мини-модели угроз (5 минут, не больше). Возьми из фазы 3 ценности и границы доверия и для каждой границы задай себе вопрос «как бы я это сломал?». Проверяй прежде всего эти места.

- **Секреты в коде и истории:** ключи, токены, пароли в исходниках и конфигах; `.env` в git (`git ls-files | grep -i env`); секреты в клиентском бандле (`NEXT_PUBLIC_*`, `VITE_*` с секретными ключами, ключи в iOS/Android-ресурсах).
- **Авторизация:** эндпоинты и серверные действия без проверки прав; проверка только на клиенте; IDOR (доступ к чужому объекту по id).
- **Инъекции:** SQL через конкатенацию строк, `eval`, `dangerouslySetInnerHTML`/`v-html` с пользовательским вводом, shell-команды с вводом.
- **Валидация входа** на сервере (zod, pydantic и т.п.).
- **Вебхуки:** проверка подписи (Stripe, Telegram secret_token).
- **Зависимости:** `npm audit --omit=dev` / `pip-audit` / `osv-scanner`, если доступны. Важны только high/critical в реально используемом коде.
- **Боты:** проверка `user_id` для админ-команд; ограничение частоты.
- **CORS** `*` вместе с credentials; отсутствие rate limit на логин, OTP и ИИ-эндпоинтах (это деньги).
- **Сессии и пароли:** cookie `httpOnly` + `secure` + `sameSite`; пароли через bcrypt, scrypt или argon2, а не sha/md5; токены сброса одноразовые и живут ограниченное время.
- **Утечки в ответах:** API отдаёт `passwordHash`, токены, чужие email или внутренние поля целым объектом из БД.
- **Ввод, который сервер использует как адрес или путь:** открытый редирект по `?next=`; SSRF (сервер ходит по URL из ввода без allowlist); загрузка файлов без ограничения типа и размера; пути из ввода в операциях с файлами.
- **ИИ и LLM:** ответ модели считается недоверенным — не попадает в `eval`, SQL, shell, `innerHTML`, пути к файлам. Права проверяются в коде, а не в системном промпте (prompt injection неизбежен). Ключ к платному API не попадает на клиент, а на эндпоинт есть лимит.
- **Гигиена зависимостей:** ровно один lock-файл, он закоммичен; нет `npm audit fix --force` в скриптах; новые пакеты не являются тайпсквоттингом (сверь название с официальным).
- **Персональные данные:** собираются только нужные; есть способ удалить аккаунт и данные пользователя, если это требуется (GDPR, App Store требует удаления аккаунта в приложении).

**Не нужно, когда:** уязвимость в dev-зависимости, которая не попадает в прод; теоретический вектор без пути эксплуатации в этом продукте. Для глубокого аудита предложи скил `security-audit`.

## R: Надёжность и ошибки
**Применимо:** `api`, `bot`, `mobile`, `web` с бэкендом.

- Таймауты на внешние вызовы; ретраи только для идемпотентных операций.
- Необработанные ошибки: пустые `catch`, проглоченные исключения, `try/except: pass`, падение всего бота от одной ошибки в хендлере.
- Пользователь видит понятную ошибку, а не белый экран или вечный спиннер (error boundaries, состояния ошибки).
- **Наблюдаемость: начни с вопросов, а не с инструментов.** Запиши 2–3 вопроса, которые придётся задать, когда что-то сломается («почему не прошла оплата у пользователя X?», «бот перестал отвечать — где?»). Проверь, может ли текущее логирование на них ответить. Метрики говорят, *что* что-то сломалось, трассы — *где*, логи — *почему*.
- Логи: есть ли вообще; есть ли в строке лога идентификатор запроса, пользователя или чата, чтобы связать события; уровни (`error` значит, что нужно действовать); нет ли в логах секретов, токенов и целых тел запросов.
- Вызовы внешних сервисов логируются метаданными: куда, статус, время, номер попытки.
- Мониторинг ошибок в проде (Sentry или аналог) — 🟠 только если есть живые пользователи. Алерт должен быть по симптому (растёт доля ошибок) и требовать действия; алерты, которые все игнорируют, хуже, чем никаких.
- Бэкапы БД, если данные пользователей хранятся у себя.
- Graceful shutdown / рестарт бота (systemd/pm2/docker restart policy).
- Миграции: применяются ли воспроизводимо.

**Не нужно, когда:** прототип без пользователей. Тогда мониторинг, бэкапы и ретраи переходят в 🟡 с условием «перед запуском».

## W: SEO, доступность, веб-база
**Применимо:** `web`, только публичные страницы. Для админок и личных кабинетов SEO пропусти.

- `<title>`, `meta description`, Open Graph и превью для соцсетей/Telegram, `lang` у `<html>`.
- `robots.txt`, `sitemap.xml`, canonical; страницы рендерятся с контентом в HTML (SSR/SSG), а не пустым `<div id="root">`.
- Семантика: один `h1` без пропуска уровней заголовков; `alt` у картинок (`alt=""` у декоративных); `label` у полей; кнопки — это `<button>`, ссылки — это `<a href>`, а не `<div onClick>`; у кнопок-иконок есть `aria-label`.
- Клавиатура: всё интерактивное достижимо по Tab, фокус виден, модалки держат фокус внутри и возвращают его при закрытии, Escape закрывает.
- Контраст текста ≥ 4.5:1 (крупного ≥ 3:1); цвет — не единственный способ передать смысл (ошибка поля показана текстом или иконкой, а не только красной рамкой).
- Формы: видимые подписи, конкретные сообщения об ошибках рядом с полем, `autocomplete` у email, телефона и адреса.
- Мобильная версия: `viewport` meta, вёрстка на 360px без горизонтального скролла, тач-таргеты ≥ 44×44px, текст масштабируется до 200% без поломки.
- Favicon, 404-страница.
- Lighthouse, если можно запустить локально.

**Не нужно, когда:** страница за логином; внутренний инструмент.

## C: Качество кода и поддерживаемость
**Применимо:** все.

Смотри по пяти осям, в порядке важности: **правильность** (граничные случаи, null и пустые значения, ошибки, гонки) → **безопасность** → **архитектура** (код лежит там, где его будут искать; нет разбросанных одинаковых условий, которые просят общую абстракцию) → **читаемость** → **производительность**. Одна структурная проблема важнее десяти мелочей.

- Сборка, typecheck и линт проходят? (Реально запусти.)
- Тесты: есть ли хоть на критичный сценарий (оплата, авторизация, главный поток). Отсутствие тестов на CSS — не находка.
- Мёртвый код, неиспользуемые файлы и зависимости (knip/depcheck/vulture).
- Гигантские файлы (>800 строк) и божественные компоненты — только если они реально мешают менять код.
- Дублирование логики в нескольких местах (особенно бизнес-правил и цен).
- Захардкоженные URL, ключи окружения, магические числа в бизнес-логике.
- Типизация: `any` и отключённые проверки в критичных местах.
- Устаревшие мажорные версии фреймворка, от которых уже нет патчей безопасности.

**Не нужно, когда:** «переписать на чистую архитектуру»; рефакторинг ради стиля; 100% покрытие тестами в MVP.

## A: Удобство для ИИ-агентов
**Применимо:** все. Эта область — причина существования карты проекта.

- Есть ли `CLAUDE.md` / `AGENTS.md` с командами и правилами (после фазы 2 есть). Есть ли в нём раздел «Границы»: что никогда не делать, о чём спрашивать перед действием.
- Правила в CLAUDE.md совпадают с тем, что реально в коде. Правило, которое код нарушает на каждом шагу, сбивает агента сильнее, чем отсутствие правила.
- CLAUDE.md короткий (≤ 60 строк), а детали вынесены в карту. Раздутый файл правил ухудшает работу агента: чем больше инструкций, тем хуже каждая соблюдается.
- Есть эталонные файлы, на которые можно сослаться как на «пиши так». Если в проекте 3 разных стиля одного и того же (три способа делать запросы, два стейт-менеджера), это находка `A`/`C`: агент будет плодить четвёртый.
- Можно ли запустить проект одной командой по README; есть ли `.env.example` со всеми нужными именами.
- Есть ли быстрая команда проверки (`lint`, `typecheck`, `test`), которую агент может прогнать после правки.
- Предсказуемая структура: понятно ли по названиям, где что лежит.
- Сгенерированные файлы помечены и исключены (агент не должен их править).
- Ложные следы: устаревший README, мёртвые папки `old/`, `backup/`, `copy-of-*`, закомментированные куски — сбивают агентов.
- Для веба: есть ли способ быстро увидеть результат (dev-сервер, `.claude/launch.json` для превью).

**Не нужно, когда:** крошечный проект из 5 файлов, где всё и так очевидно.

## U: Продукт и UX
**Применимо:** `web`, `mobile`, `bot`.

- Главный сценарий проходится без тупиков: пустые состояния, ошибки, загрузка, подтверждения.
- Онбординг и первое впечатление: что видит новый пользователь (для бота — `/start`).
- Формы: валидация с понятными сообщениями, не теряются введённые данные при ошибке.
- Аналитика главного действия — только если продукт уже ищет рост.
- Тексты: опечатки, смешение языков, заглушки «Lorem ipsum» и «TODO» в интерфейсе.
- Мобильная вёрстка и тач-таргеты (web); Dynamic Type и тёмная тема (iOS) — по ситуации.

**Не нужно, когда:** советы уровня «добавьте геймификацию» без связи с целью продукта. Продуктовые идеи давай отдельным коротким списком «идеи», без вердикта 🔴/🟠.
